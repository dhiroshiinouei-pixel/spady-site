# 口コミ365：送信IDと予約検知（確認用）
- 既存台帳の「口コミ365_送信・予約管理」で、1通ごとに既定のランダムIDと送付先店舗を対応させる。再送も新しい行。行の並べ替えは表全体で行う。
- LPとカレンダーは従来と同じ。IDなし・不正形式・重複パラメータは無視。クリック／スクロール／カレンダー表示では検知しない。入力された情報は取得しない。照合用IDをHubSpot・Metaへ送らない。
- 確認用ホストからの通知だけを中継。Apps Scriptは共有鍵で署名と時刻を確認し、一意のIDと店名のある行のF列だけに最初の検知日時を記録する。本部確認列Gは独立。公開経路はクライアントからの検知を受け取るため、署名は中継経路の認証でありHubSpot予約の認証ではない。転送・流出したIDや無信号・通信失敗等の影響を受ける。正式な成果確認には使用しない。

## 接続は既定で無効
1. Google Apps Scriptで新規のスクリプトを作成し、docs/kuchikomi365-referral-ledger.gs を貼る（既存の予約メール通知スクリプトとは別）。試験時は、同じ名前・列順のタブを持つ、実データを含まない非公開のコピーを使う。3行目以降にsp_と24文字の新規ID、B列に架空の店舗名を入れる。スプレッドシートのタイムゾーンはAsia/Tokyo。
2. スクリプトプロパティに REFERRAL_SHEET_ID（試験台帳のID）と REFERRAL_SECRET（十分な乱数由来の32文字以上の鍵）を設定する。所有者として実行するウェブアプリでサーバーからアクセスできるようデプロイする。URLや秘密鍵はコミットしない。キー不一致はシートに触れない。
3. Cloudflare PagesのPreview環境に、K365_REFERRAL_WEBAPP（/exec URL）とK365_REFERRAL_SECRET（同じ鍵）を設定し、ドラフトのプレビューだけ再デプロイ。Productionには設定しない。停止する場合はPreviewの設定を無効化して再デプロイし、Apps Scriptのデプロイも停止。
4. ローカルの模擬テスト: node --test test/k365-referral.test.mjs。実際のHubSpot通知・本部での予約・正式な店舗照合は、別途承認を受けた検証が必要。無断で実予約を作成しない。

## 半自動のLINE連絡
- 既定は通知オフ。接続の模擬テストと通知先の確認の後にだけ、Apps Scriptの `REFERRAL_OWNER_EMAIL_ENABLED` を `true` にし、メール送信権限を承認して再デプロイする。
- 送信日時（E列）が記録済みで、最初の予約完了反応を記録した場合に限り、`info@spady.net` に店名入りのLINE連絡文を送る。店名は実際の予約者ではなく台帳上の送付先。顧客の電話番号、メール、入力内容、送信IDは送らない。
- 井上さんが確認し、既存のLINEで本部へ送る。本部への自動送信や本部確認列の自動更新は行わない。メール送信エラー時もF列は残る。重複を避けるためメールは自動再送せず、台帳とApps Scriptの実行ログで確認。
