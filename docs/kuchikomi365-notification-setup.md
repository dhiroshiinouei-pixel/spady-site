# 口コミ365 予約検知通知の設定（公開前）

通知先は `info@spady.net` に設定済みです。

## 状態
- このファイルはGoogle Apps Scriptに貼るための**テンプレート**で、GitHubに置いただけでは送信されません。
- Spadyページの `CONFIG.appsScriptUrl` は未設定。したがって通知は**まだ届きません**。
- HubSpot予約フォームの `meetingBookSucceeded` が埋め込みから届くかは本番で未検証です。
- メールは「ページが検知した予約イベント」を知らせるもので、HubSpotの実際の予約や紹介報酬の確定記録ではありません。

## 稼働させる手順
1. `https://script.google.com/` で通知用Apps Scriptを作成する。
2. `docs/kuchikomi365-notification.gs` の内容を貼り付け、保存する。
3. 新しいデプロイ→ウェブアプリを選び、「自分として実行」「全員がアクセス可能」に設定する（公開エンドポイントになる点に留意）。
4. 初回のメール送信権限を許可し、発行された `/exec` で終わるウェブアプリURLを取得する。
5. `public/kuchikomi365/booking.js` の `CONFIG.appsScriptUrl` にURLを設定する。
6. スパム・誤検知のリスクを理解し、本部と相談して承認されたテスト予約を実施する。実際の予約と通知を照合する。
7. Meta Pixelの `CONFIG.metaPixelId` を設定する場合は、プライバシー説明・同意の動作を確認した後、イベントマネージャのテストイベントで確認する。

## 制約
- 通知内容に顧客氏名やメールアドレスは含まれません。
- 外部フォームで直接予約した場合は、このページでは検知できません。
- ページ内の紹介者表示は変更不可ですが、HubSpotの「ご相談内容」欄は編集可能です。
- Apps Scriptの公開URLへ偽のPOSTが送られる可能性があります。簡易上限を付けていますが、確定した予約データの代替にはなりません。
- 正確な紹介者帰属や成約報告は本部との照合が必要です。

サイト本番 `main` へマージせず、ドラフトPRで確認してください。

## LP改修版：表示とイベント定義

紹介者は親LP上で固定表示。予約は本部の編集可能なフォームで行う。埋め込み予約フォームに単一の `consultation_details` を付ける。公開URLの `utm_*` は既知5項目のうち、英数字と `_.+-`（100文字以内）の値だけを予約先へ渡す。個人情報を広告URLやUTMに入れないこと。以前の埋め込み補助スクリプトは親の全クエリを再転送するため、同じ本部URLを直接 iframe に埋め込む方式へ変更した。LPから外部への遷移は設けず、カレンダーが読み込めない場合はその場で再読み込みできる。JavaScriptを無効にしている場合は、有効化が必要。プレビューは noindex であり、URLへのアクセス制限ではない。

| 観測対象 | Metaイベント（設定・同意済みの場合のみ） | 意味 |
| --- | --- | --- |
| LP表示 | `PageView` | 同意状態でPixelが初期化されたページ |
| 主要CTA | `K365_BookingCTAClick` | `placement`: header / hero / consult / sticky |
| 予約セクション表示 | `K365_ReservationSectionView` | セクションが初めて表示範囲に入った。フォーム入力を表さない |
| 埋め込みの完了通知 | `Schedule` | 親LPで検証条件を満たす通知を一度観測した。予約の受理・参加・契約と別 |

完了通知は `https://meetings-na2.hubspot.com` と当該iframeの `contentWindow` の両方が一致し、`meetingBookSucceeded: true` と予約応答内の開始情報がある場合だけ受け付ける。オフライン扱いは対象外。実配信のHubSpot公開スクリプトの成功条件に合わせたが、実予約由来の通知受信は未確認。HubSpotが形式・配信originを変えた場合は検知しなくなる可能性がある。親LPは予約情報の中身を保存せず、送信もしない。Apps Scriptへの通知に含めるのはイベント種別、固定紹介文、ページ単位の識別子、検知日時、クエリなしのLP URLのみ。この公開先からの通知は本人性を保証しない。必要なら通知URLを未設定のままにし、本部の予約台帳を正とする。

重複排除は同じLP読み込み中に一度。LP外の予約、同意がない行動、ブロッカーで止まった計測は欠測。過去の行動の再送はしない。広告の同意状態はLPの専用キーで保持し、設定変更はフッターから。HubSpot予約フォーム側の案内・同意は別。比較時は同じ条件・期間で、Metaの同意済み表示あたりの埋め込みScheduleと、本部で受理した紹介予約数を分ける。相談の質は実施率・対象業種との適合等を本部との合意の上で確認する。リード数から成約を推定しない。

## 予約者の入力内容をSpadyにも共有する場合（本部の承認・設定が必要）

- 現在のSpady通知は「埋め込みで完了通知を観測した」ことだけを伝える。予約フォームの入力内容は転送・保存しない。既存通知とは別に、本部が受理した予約を情報源とする。
- 本部のHubSpotで、Spady専用の予約リンク／予約ID等で対象を識別する。編集可能な「ご相談内容」の文言だけで対象を判定しない。相談フォームで、共有先（Spady）、利用目的（問い合わせ対応・紹介の照合等）、共有項目を示し、必要な同意を得る。広告計測の同意とは別。自由記述や電話番号は必要性を確認した上で選ぶ。
- 本部の権限で、対象予約だけを閲覧できる制限付きビュー、または必要な項目だけを `info@spady.net` に知らせる仕組みを用意する。他の予約やコンタクトへの広い閲覧権限は不要。HubSpotの標準社内通知の宛先はアカウントのユーザー・チームなどであり、外部アドレスへの自由な配送は前提にしない。予約フォームの質問がコンタクトの項目か、予約ごとの質問かで取得方法が異なるため、本部が現行の項目・契約・権限で確認する。
- 本部側が設定できれば、埋め込みからの予約を本部の受領元で扱える。一方、通知設定や閲覧権限を本部で用意できない場合には、まず明示的に承認された最小項目を本部から共有する運用に限る。親LPや公開Apps Script URL経由の個人情報収集は追加しない。現状は未接続。今回は実予約・送信なし。
